1. Purpose and Method

tap-project-overview.md describes TAP as "a structured system that combines carefully controlled AI assistance with code-enforced quality gates," listing four gate categories in its "Programmatic Quality Gates" section and a condensed per-tracker field list in its Technical Appendix. This report is the exhaustive, verified companion to that summary: every field comes from the actual SCHEMA.md file — as of 2026-09-02, all five trackers have one, including new prosecution/cabinet-level/SCHEMA.md and tracker/SCHEMA.md, both written this session to consolidate what had only lived as prose in tap-system-doc.md — and every gate was located by reading the actual script, not inferred from a doc's description of it. Where the overview's framing turned out to overstate what a script actually does, that's called out explicitly in Section 8 rather than silently repeated. A SCHEMA.md documenting a tracker's fields is not the same thing as a gate enforcing them — see Section 8 for which trackers actually have a validation gate behind their schema and which don't.

2. Schema Fields — CLA (Cabinet-Level Accountability)

Field Type Notes
id string Kebab-case slug, matches filename minus .json. Added 2026-08-22; must never be edited after creation.

status string Current state of the matter; classified into short display labels by index.html at render time.
contested boolean Whether the characterization is genuinely disputed, not adjudicated.
incident_summary string Full narrative of what happened.
elements_required array of strings The legal/factual elements the entry's claim rests on.
evidence array of objects Each item: type, description, source_url, maps_to_element.
rebuttal_anticipated string The strongest good-faith counter-argument.
comeback string The response to that rebuttal.
cause string Interpretive framing, explicitly flagged as analysis rather than sourced fact.
confidence_note string Sourcing strength and how to frame the entry in debate use.
last_verified date Renamed from last_updated 2026-09-01 to match the other two curated trackers.
date_added date Set once at creation, never edited afterward.
section_summaries object incident_summary, confidence_note — added 2026-07-21, see Section 4 of the batch-picker/audit reports this session for the backfill history.

5. Schema Fields — User Topics

Source: community-topics/SCHEMA.md. Deliberately a lighter rigor tier — no elements_required/evidence, primary_proponent, or corporate_beneficiaries/estimated_*_impact.

Field Type Notes
id string Kebab-case slug; must exactly match the target tracker's id for cross-links to resolve.
topic string TAP's own cleaned-up framing; the entry's title everywhere on site.
submitted_claim string Submitter's raw text, verbatim, never cleaned up.
verdict string confirmed | partially_confirmed | unable_to_verify | misleading_as_stated.
summary string 2–4 sentences, plain language.
sources array of objects name, url.
related_entries array of objects tracker, id, note — points at an overlapping curated entry rather than duplicating its research.
submitter_source_link string or null URL the submitter provided, if any.
date_submitted date The form response's Timestamp.
date_added date Set once, never edited.
promoted_to string (optional) tracker/id if this topic became (or was folded into) a curated entry. Omitted entirely if not applicable.

No section_summaries field — explicitly out of scope for this tracker (spec sec-4, see Section 7 below).

8. Where the "Gates" Framing Overstates What the Code Does

Two things worth being precise about if describing this system to someone else:

publish.py — what actually goes live — does no schema validation at all. Read in full this session: it loads every *.json file in an entries folder, checks only whether the filename is on the manual exclude list, and writes a blind combined array to the site's data/*.json. There is no field-presence check, no type check, nothing. The overview's line that the Reporting tracker is "not subject to the same reject-if-incomplete gate as the four trackers above" implies the four curated/User-Topics trackers do have one at publish time — they don't. The only field-completeness gate that actually exists is in the two index-builder scripts (Section 7), and it only skips an incomplete entry from the secondary index.json/Markdown output, not from the live public JSON. An entry missing a required field would still publish to the actual site.

Schema enforcement of this kind exists for only two of five trackers. build_prosecution_index.py (CLA) and build_deregulation_index.py (CDR) both have a real validate_entry() gate. GSR has no build_*index*.py script at all. User Topics has neither a build nor a validate script. Reporting is explicitly out of scope by design (it's raw archive data, not curated per-entry claims). So "every tracker enforces a strict data schema... files lacking complete fields are rejected" (the overview's Technical Appendix framing) is accurate for CLA and CDR's secondary artifacts specifically, and not literally true anywhere else in the system.

Neither of these is a bug — the actual safety net for schema completeness, per tap-database-update-process.md sec-9's own "Manual vs. Claude-required" table, is Claude reviewing the diff before proposing a commit, plus the git diff data/ review step in publish.py's own printed instructions. The gates that exist are real and do what they say; there just isn't a comprehensive one sitting in front of the actual publish step.

A SCHEMA.md file is documentation, not a gate. As of 2026-09-02 all five trackers have one (Section 1), but that doesn't change which trackers have an actual validation script behind their schema — still only CLA and CDR (their index-builders' validate_entry()), still nothing for GSR, User Topics, or Reporting. Writing prosecution/cabinet-level/SCHEMA.md and tracker/SCHEMA.md this session closed a documentation gap, not an enforcement one — worth keeping the two distinct when describing this system to someone.

9. Process Gates (Human-in-the-Loop, Not Code)

These are real control points the documentation calls "gates" (tap-submission-triage.md's own changelog: "count-and-confirm gate added to sec-3"), but they're enforced by written instruction and Claude's discipline in following it, not by any script that could mechanically block a bad output. Listed separately so the word "gate" isn't read as implying code enforcement where none exists.

  • Count-and-confirm stop (tap-submission-triage.md sec-3, tap-update-request-triage.md sec-3): report the untriaged count and stop for Joe's go/wait decision before starting triage.
  • Batch-size ask-if->6 rule: every recheck sweep and candidate-discovery workflow surfaces the ~6-entry batch-size guidance and asks how to split, rather than silently processing a larger batch.
  • AskUserQuestion escalation points: tracker-fit ambiguity (a candidate could plausibly belong to two curated trackers), GSR entry-scope decisions (separate/merge/skip), curated-vs-User-Topics calls when genuinely unclear, and a batch-number mismatch between the memory file and git log.
  • advisor() call convention: standing practice before drafting JSON edits in the CLA/GSR recheck sweeps, catching gaps like an uncited AI-summary source or a wrongly-folded thread — see the standing lessons in the CLA recheck reference memory.

10. Scripts That Are Not Gates

Included for completeness, since the request was for "all... scripts and functionality" — these exist in the same directories as the gates above but don't validate, block, or route anything:

  • backfill_date_added.py, prosecution/backfill_last_updated.py, prosecution/rename_last_updated_field.py — one-off historical migration scripts, already run, not part of any ongoing workflow.
  • tracker/export_cluster_batch.py — exports a candidate batch to file for the shelved agy pre-pass; a data-shaping utility, not a check.
  • tracker/find_candidate_entries.py's matched_trackers field — explicitly documented as "a hint from the mechanical prefilter, not binding" (tap-candidate-discovery.md sec-4.3); verified during research, never trusted as a gate.
  • government-services/cluster_disruption_entries.py / tracker/cluster_disruption_entries.py (identical file, present in both locations) — groups likely-duplicate raw News entries by keyword; a grouping aid for candidate discovery, not a pass/fail check.
  • tracker/clean_existing_categories.py — one-off retroactive fix for two known scraper bugs in already-scraped data.
  • tracker/scrape_archive.py, tracker/build_dataset.py, tracker/parse_post.py — the ingestion pipeline itself. parse_post.py does whitelist-match category labels against KNOWN_CATEGORY_LABELS internally, but that's parsing logic, not a gate on AI-authored content — Reporting entries are scraped, not written by Claude.
