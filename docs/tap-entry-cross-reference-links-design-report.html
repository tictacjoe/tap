TAP Entry Cross-Reference Links — Design Report

The Accountability Project — Docs

Session Scope: A design question raised in passing — whether an entry card can link to another entry it mentions by name in prose — that turned into a code investigation of tap-site/index.html's existing entry-rendering and related-entry-link infrastructure. The investigation found that the site already has a working mechanism for this, but it is wired up for only one of five trackers. No code has been written and no decision has been made on how to extend it; this report captures the finding and the open choice.

1. Session Overview

The question was prompted by a concrete example already live in the Cabinet-Level Accountability tracker: the rfk-jr-acip-apa-violation-2026-03.json entry's status field contains the sentence "See also this tracker's separate trump-childhood-vaccine-eo-2026.json entry for Trump's May 29, 2026 executive order...", and that same entry is itself referenced by name from cdc-leadership-vacancy-crisis-2026.json in the Government Services tracker ("documented separately in this tracker's Government Services database, cdc-leadership-vacancy-crisis-2026.json"). Both are plain prose today — the filename is typed out, but nothing is clickable. Before proposing a fix, tap-site/index.html was read to determine whether any linking mechanism already existed, rather than assuming one would need to be built from scratch.

2. Problem and Motivation

TAP entries frequently reference each other by id — an entry's incident_summary or status field will point a reader to a related entry in the same or a different tracker for detail the current entry doesn't want to duplicate or re-verify. This is a deliberate and recurring editorial pattern (the RFK Jr./CDC example above is not a one-off), but it currently costs the reader a manual search: they have to read the mentioned filename, leave the entry card, and search for it themselves. A real link would let the reader jump straight to the referenced entry, the way promoted_to and related_entries already let a User Topics submission jump straight to the curated entry it overlaps with.

3. Existing Mechanism Found

tap-site/index.html already implements exactly this kind of jump, but only for the community-topics tracker:

  • entry.promoted_to (a single "tracker/id" string) and entry.related_entries (a list of {tracker, id, note} objects) are schema fields documented in tap-data/community-topics/SCHEMA.md.
  • The renderer (index.html:1803-1823) turns each into an <a class="related-entry-link" data-tracker="..." data-id="..."> element.
  • A click handler (jumpToRelatedEntry, around index.html:2260-2281) locates the target card via document.querySelector('.entry[data-entry-id="' + CSS.escape(id) + '"]') — every card is stamped with data-entry-id at render time (index.html:1861) specifically so this lookup works — and jumps to it.

The other four trackers (Cabinet-Level Accountability, Corporate Deregulation, Government Service Redirection, Reporting) have no equivalent field in their schemas, and their renderer branch (index.html:1833-1846, the "prosecution (default)" case that Cabinet-Level Accountability entries like rfk-jr-acip-apa-violation-2026-03.json fall into) renders incident_summary and status as plain escaped, search-highlighted text (hl(entry.incident_summary), hl(entry.status)) with no linkification step. The click-handling and DOM-lookup plumbing is generic and already works across trackers (it's keyed on data-tracker/data-id, not hardcoded to community-topics) — what's missing is (a) a structured field for the other trackers to put a cross-reference in, or (b) a render-time step that finds and links existing prose mentions, and either way a renderer change so the default branch emits the same kind of related-entry-link markup the community-topics branch already does.

4. Approaches Considered

Approach A — Extend the related_entries structured field to all trackers. Add related_entries to the schemas for prosecution/cabinet-level, deregulation, government-services, and reporting; wire the default renderer branch to emit the same callout community-topics gets. No new click-handling code needed — the DOM-lookup mechanism is already generic. Going forward, a new cross-reference gets captured as structured data instead of prose. Leaves the existing prose mentions (the RFK Jr./CDC pair and however many others exist across ~100+ entries) as plain text unless each is individually retrofitted into the new field by hand.

Approach B — Auto-linkify inline prose mentions. At render time, scan incident_summary/status text for patterns like <some-id>.json and rewrite matches into the same related-entry-link markup. Automatically picks up the existing backlog of prose cross-references with no manual retrofit. Requires building an id→tracker lookup table (a given id, like trump-childhood-vaccine-eo-2026, doesn't self-identify which tracker's JSON file it lives in) and interleaving a second regex pass with the existing highlightMatches()/hl() search-highlighting pipeline (index.html:1591-1608), which already does one escape-then-regex-replace pass over the same text — two independent regex-based rewrites over the same string need to compose without corrupting each other's HTML output.

Combination. The two are not mutually exclusive: A gives clean, low-risk data going forward; B clears the existing backlog automatically. Doing A alone without B leaves the RFK Jr./CDC example itself unlinked unless someone also manually adds a related_entries entry to it.

No approach was selected in this session — the question was left open for a decision on scope (schema change only, backlog auto-linkify only, or both) before any implementation.

5. Status and Next Steps

Nothing has been built. This report documents an investigation and the resulting open design choice, raised during an unrelated session and not yet carried into a brainstorming or planning flow. The next step, if this is picked up, is a decision on Approach A vs. B vs. both, followed by the normal brainstorming-to-writing-plans flow before any schema or index.html changes are made — this touches both repos (tap-data schemas and tap-site/index.html), so per the two-repos-both-need-a-commit rule, any implementation would need commits in both.
