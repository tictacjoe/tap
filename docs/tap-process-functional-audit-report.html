1. Audit Method and Scope

The existing tap-sweep-stage-summaries.md table (six processes, each broken into numbered stages) was used as the skeleton. Each stage was checked against tap-database-update-process.md, tap-candidate-discovery.md, tap-submission-triage.md, and tap-ops-runbook.md, then verified directly against the live repository rather than judged on documentation alone — the same standard the project's own prior documentation audit used.

Verification meant two different things depending on the stage. Stages implemented by a read-only, non-mutating script (staleness finders, schema/field validators) were actually executed this session against the live datastore, and their real output is reported below. Stages implemented by a mutating script (check_for_new_posts.sh, which scrapes and writes; find_candidate_entries.py, which writes to candidates.json; publish.py, which writes to a second repo) were not executed, to avoid changing tracked repository state as a side effect of an audit — those were verified by reading the script and cross-checking its documented behavior against its actual code, not by running it live. This distinction is called out per stage below.

Per this session's added request, every stage also carries an automation-suitability read: whether it is a good candidate for the deterministic, script-plus-feedback-loop pattern designed in the prior session (tools/batch_picker.py, not yet built), or whether it needs to stay Claude-required. Section 11 synthesizes the pattern across all six processes.

2. Cross-Cutting Findings

Four things surfaced that cut across more than one process, ahead of the per-process detail:

  1. Directory-layout inconsistency between trackers. Cabinet-Level Accountability's 164 entries live flat under prosecution/cabinet-level/*.json; Corporate Deregulation and Government Service Redirection both use an entries/ subfolder (deregulation/entries/, government-services/entries/). This isn't documented as a quirk anywhere and it broke this session's first attempt to run validate_section_summaries.py against prosecution (it was pointed at a nonexistent prosecution/cabinet-level/entries). Any future tool that treats the three curated trackers uniformly — including a generalized version of the batch-picker pilot — needs to special-case this.
  2. A previously-unflagged backlog in the section_summaries card-skim feature — corrected after follow-up investigation, and since fully closed. Running validate_section_summaries.py live against all three curated trackers found entries missing the field: 17 of 164 Cabinet-Level entries (this session's first pass undercounted this as 6, due to a truncated command; corrected here), 24 of 257 GSR entries, and 1 of 56 Deregulation entries — 42 entries, roughly 80 individual summary lines. Direct inspection of sample files showed the underlying content (incident_summary, what_changed, estimated_impact, confidence_note) is fully present and researched in every flagged entry — nothing is actually missing from the substantive record. section_summaries is a separate, designed field (approved 2026-07-21, docs/superpowers/specs/2026-07-21-card-section-summaries-design.md) holding short hand-written condensations that power a bolded skim-line on each site card; it was fully backfilled once for all entries that existed at the time (commit 5b3b895 for Cabinet-Level, matching passes for the other two trackers) but the workflow step requiring it be written alongside the underlying field hasn't been consistently followed for entries added since. This is a drafting backlog (write ~80 short condensations of already-researched content), not a research gap. Update (2026-09-03): closed the day after this audit — commits b280f5e (17 Cabinet-Level), af343ad (24 GSR), and 7067756 (1 Deregulation), all 2026-09-02, backfilled exactly this finding's gap. Re-running all three validators live today confirms 164/164, 257/257, and 56/56 complete. Worth noting: this was a one-time manual catch-up sweep, not the pre-commit enforcement this report recommends in Section 12 — no .git/hooks/pre-commit exists in this repo, so the same drift (new entries added without their section_summaries) can recur silently until the next manual check or the automation actually gets wired in.
  3. No traditional log files exist anywhere in this repository. find . -iname "*.log" returned zero results in tap-data. Every audit trail in this project is a git commit, a tracked JSON field, a markdown notes file, or an external Google Sheet column — see Section 10.
  4. The project already ran one real experiment in automating a judgment-heavy stage with an AI control loop, and it failed silently. The agy research-pre-pass pilot (Section 7 below) is the single most relevant precedent for this audit's automation-suitability calls and is referenced repeatedly below rather than re-explained each time.

9. Universal Publish & Deploy Sequence

Shared by all six processes (tap-database-update-process.md sec-7–8; tap-ops-runbook.md sec-5). Not executed live this session, since every step either commits or pushes to one of the two repos. Verified by reading publish.py's invocation and the documented output format only.

The sequence is: commit-and-push the working repo first (a step documented as having actually been skipped once, 2026-07-18) → run publish.py --working ~/gjoe/tap-data --site ~/gjoe/tap-site → read its printed per-tracker counts and stop if any look wrong → review git diff data/ in the site repo as the last safety check before anything goes public → commit and push the site repo → confirm both repos show origin/main on their latest commit → verify the live site with curl.

Every individual command here is deterministic and already scriptable end-to-end — a single wrapper script could run the whole sequence and halt on the first unexpected count or diff. The two things worth keeping outside full automation are the count/diff review itself (the project's own "don't publish blind" rule) and the commit-message content, both of which are explicitly there as a last human/Claude check before something goes live on a public site — see Section 11.

10. Logfile and Audit-Trail Reference

There are no traditional *.log files anywhere in tap-data (confirmed: find . -iname "*.log" returns nothing). The project's audit trail is distributed across several different mechanisms instead:

  • Git commit history, both repos. The primary log for every substantive change. Batch numbers for CLA/GSR/Deregulation recheck sweeps are derived by grepping commit subjects (git log --oneline | grep batch), not from any counter file — this is also the source of the batch-number off-by-one drift the prior session's batch_picker.py design targets.
  • Per-batch research/recheck notes, tracker/output/research-briefs/*.md, thread-qualified filenames: cabinet-recheck-batchNN-notes.md, deregulation-recheck-batchNN-notes.md, round4-batchNN-notes.md (Reporting candidate discovery). GSR's equivalent files live in government-services/gsr-recheck-batchNN-notes.md instead (moved there at batch 25–26). Written only when triggered — real corrections only for the three recheck sweeps, every batch regardless of outcome for round-4 discovery.
  • tracker/output/candidates.json — a structured, git-tracked log in its own right: every candidate's status/outcome_note/outcome_date fields are a queryable record of every triage decision ever made by this process, not just a working queue.
  • The Google Sheet's Status/D–F columns — the entire audit trail for submission triage; there is no local file at all for this process. A declined submission's only record is that row.
  • ~/gjoe/AI_Data/session-logs/ — Claude Code's own session-log auto-save. Explicitly documented as unreliable for research provenance (tap-candidate-discovery.md sec-4.5): its save script's jq filter keeps only .type == "text" blocks and strips tool_use/tool_result content, so WebSearch queries and results never appear there. Confirmed by the project itself grepping a completed session's log for a heavily-researched name and finding zero hits. Don't treat this as a research log for any process.
  • output/research-briefs/batchNN-agy.log — the shelved agy pilot's own CLI logs, pinned to predictable paths via --log-file specifically so verify_research_brief.py could find them without guessing among agy's auto-timestamped default log location (~/.gemini/antigravity-cli/log/cli-*.log). Historical, from the two pilot batches only; not part of the active workflow.
  • No structured run-log exists yet for the proposed batch_picker.py pilot (prior session's design, not yet built). Its planned tools/batch_picker_log.jsonl would be the first genuinely structured, purpose-built log file in this repository — everything above is either prose, a Sheet, or git history repurposed as a log rather than designed as one.

11. Automation-Suitability Synthesis

Three consistent categories emerged across all six processes, not just for Cabinet-Level:

Deterministic/structural stages are uniformly a good fit, and most are already scripted: staleness detection (all three curated trackers), schema/field validation, JSON-validity checks, the chronology checker, and the mechanical parts of publish/deploy. The one deterministic stage that is not yet scripted despite being a good candidate is exactly the one the prior session's batch_picker.py design targets — batch selection for the recheck sweeps, currently redone by hand from git log every session.

Judgment stages are uniformly a poor fit for full automation, and this project already has direct evidence, not just a general presumption: the agy research-pre-pass pilot (Section 7) automated primary research on a judgment-heavy stage and failed via confident, undetected fabrication — not a crash, not an obvious error, a plausible-looking brief built from nothing. A dedicated, validated mechanical gate (verify_research_brief.py) still wasn't sufficient on its own, because it can verify that tool calls happened and URLs resolve, but not that the reasoning is honest. The safe pattern this project has actually converged on is a mechanical gate around a judgment step, never a replacement for it: verify_research_brief.py, validate_official_field.py, and check_chronology.py all follow this shape. Any future automation of a judgment stage in this project should assume the same ceiling applies.

A third category is easy to mistake for the second: stages kept manual on purpose, not because they're hard to automate. The submission queue's count-and-confirm stop before triage begins, and every "don't decide alone, use AskUserQuestion" branch (tracker-fit ambiguity, GSR scope decisions, curated-vs-User-Topics calls) are all things a script could resolve unattended — the underlying logic is often simple. They're gated instead because Joe specifically wants a checkpoint there. These shouldn't be scored as poor automation candidates the way research is; they should be left alone as intentional design, and a future automation effort should preserve the gate rather than try to remove it.

12. Findings Summary and Next Steps

New findings from this session, not previously tracked anywhere found:

  1. A section_summaries drafting backlog — 17 Cabinet-Level, 24 GSR, 1 Deregulation entries (42 total, ~80 individual summaries) missing the hand-written card-skim field, all with the underlying substantive content already fully present (Section 2, finding 2). Separate from the staleness/recheck backlog; not currently on any tracked list. Update (2026-09-03): closed the next day, via a manual backfill sweep (commits b280f5e/af343ad/7067756, 2026-09-02) rather than the pre-commit automation recommended below — the recommendation itself is still unimplemented, so the same drift can recur.
  2. Directory-layout inconsistency between Cabinet-Level (flat) and GSR/Deregulation (entries/ subfolder) — undocumented, and a real trap for any tool (including the prior session's proposed batch_picker.py) that assumes uniform tracker layout. Still open as of 2026-09-03 — no rename or special-casing has been done; confirmed by direct directory listing and a CLAUDE.md/docs grep turning up no rename commit or tracked TODO.

How this bears on the batch-picker pilot from the prior session: the audit confirms the pilot is targeting the right kind of stage — a deterministic, currently-manual step (batch selection) sitting right next to already-scripted deterministic steps (staleness detection, validation) in the same process. It also surfaces three more concrete candidates for the same treatment, roughly in priority order: wiring validate_section_summaries.py into the pre-commit step of Stage 3 across all three curated trackers (would have caught finding 1 automatically going forward — still not done as of the 2026-09-03 update, even though finding 1 itself was manually cleared); a single wrapper script for the "push both repos" publish sequence (Section 9), which has a documented history of being the exact kind of step humans and Claude both forget; and, once the Cabinet-Level pilot is proven, the same batch-picking logic generalized to GSR and Deregulation. As of 2026-09-03, batch_picker.py itself has still not been built (find . -iname "batch_picker*" in tap-data returns nothing) — the pilot remains a design, not a working tool.

What this audit did not do: execute any mutating script (check_for_new_posts.sh, find_candidate_entries.py, publish.py), since that would change tracked repository state as a side effect of an audit rather than a deliberate update. Those stages' functional status rests on code-and-doc review, not a live run, and should be read with that caveat.
