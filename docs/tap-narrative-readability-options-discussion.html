Making Dense Narrative Fields More Readable — Options Discussion

The Accountability Project — Docs

Session Scope: Research only, explicitly not carried into brainstorming's design/spec/implementation flow — the user asked for a discussion of options, then said "this is just research, don't make changes" partway through a clarifying-questions pass. No field scope was decided, no design was chosen, and nothing was implemented. This report captures the idea space and the relevant existing precedent for a later session to pick up.

1. Problem

Some TAP tracker entries' detailed narrative fields — incident_summary, and especially status — read as dense, citation-heavy prose that's accurate and complete but hard for a human to skim; the comparison drawn in-session was to reading Shakespeare: it makes sense, but only after real unpacking. The rfk-jr-acip-apa-violation-2026-03.json entry in Cabinet-Level Accountability was the concrete example: its status field has accumulated a new "Update:" or "Update 2026-0X-XX:" clause at nearly every recheck since the entry was created, all inside one unbroken paragraph. The goal raised was to make that kind of field easier to read without changing or shortening the underlying narrative itself, which stays the authoritative full record.

2. Existing Precedent: the section_summaries Field

An adjacent problem was already solved once. docs/superpowers/specs/2026-07-21-card-section-summaries-design.md (approved and implemented) added a section_summaries field: a hand-written, ~80–160 character bolded skim-line rendered above the full paragraph for qualifying sections, written by Claude in the same pass as the underlying text. Two relevant decisions from that spec carry directly into this discussion:

  • Bolding the first sentence, client-side, with no new data was rejected. A sample across all three hand-authored trackers found first "sentences" (by punctuation) running 148–283 characters median, because these fields are written with " -- "-joined compound clauses rather than short topic sentences — a bolded first sentence would usually be a multi-line fragment that buries the point after the dash, not a skimmable summary.
  • A scripted/LLM-generated summary was rejected. It would add an API-key dependency and per-publish cost to a pipeline that currently has none, be non-deterministic (polluting the git diff review step the publish workflow relies on), and contradicts an existing design choice (index.html:925-928) to avoid LLM-generated one-liners for the same reasons.

The chosen approach — hand-authored, deliberately short, written in the same editorial pass as the field it summarizes — is the direct ancestor of "idea 3" (a summary layer between the skim-line and the full text) discussed below, and its known cost and staleness-risk profile apply to that idea almost unchanged.

3. The Coverage Gap: status Has No Skim-Line

section_summaries is scoped, per the 2026-07-21 spec, to incident_summary and confidence_note for Cabinet-Level entries (and what_changed/estimated_impact/confidence_note for Deregulation and Government Services) — it does not cover status. That's notable because status is where density actually accumulates over an entry's life: it's the field that gets a new clause appended at every recheck, while incident_summary is comparatively static after an entry is first written. The RFK Jr. entry's status field — the one that prompted this discussion — currently has zero skim-line coverage under the existing design, even though it's the densest field in the entry.

4. Three Ideas, Discussed

Idea 1 — Bold key phrases within the existing narrative. Closest in spirit to the already-rejected "bold the first sentence" approach, but not identical — it targets phrases scattered through the paragraph rather than only its opening clause, which sidesteps the specific compound-sentence failure mode the 2026-07-21 spec found. It doesn't sidestep the harder problem underneath, though: deciding what counts as a "key phrase" is a judgment call, not a mechanical rule, so it needs either a hand-authoring step (inheriting the same staleness risk section_summaries already carries and explicitly left unsolved) or an automated heuristic the prior spec was already skeptical of trusting for exactly this kind of field.

Idea 2 — Force more paragraph separation. The cheapest of the three by a wide margin, because the raw material for it may already exist in the text: status fields already use "Update:"/"Update YYYY-MM-DD:" as an informal but fairly consistent marker for each addition (visible directly in the RFK Jr. entry — five such markers in one unbroken string). A purely client-side render change — split on that marker and emit separate paragraph elements instead of one block — could improve every existing entry immediately, with no hand-authoring, no data migration, and no new field to keep in sync or let go stale. The tradeoff is that it leans on an editorial convention rather than a schema-enforced structure, so its reliability is only as good as how consistently that convention has actually been followed across ~100+ entries (not verified in this session).

Idea 3 — A new medium-density summary layer (prose or bullets), between the existing short skim-line and the full narrative. The most thorough of the three, and the most expensive: real per-entry authoring effort (the short skim-line backfill alone was sized at ~284 summaries across 104 entries in the 2026-07-21 spec's own accounting, and a genuinely thorough medium-tier summary is more work per entry than an 80–160 character line), plus a second independent staleness surface — every recheck's new "Update:" clause would need the medium summary revisited too, on top of the short one, and the original spec already declined to build automated staleness detection for just the first layer.

5. A Cross-Cutting Technical Constraint

Whichever idea (or combination) gets pursued, it has to compose with how these fields already render: hl(entry.status) runs the raw text through escapeHtml() and then a regex pass (highlightMatches()) that wraps search-term matches in <mark> tags. Any approach that injects its own markup into the same field — bolded phrases, paragraph-break tags — has to interleave correctly with that existing escape-then-highlight step rather than fight it. This is the same composition concern already raised in the entry-cross-reference-links discussion for auto-linkifying .json mentions in prose — it's becoming a recurring shape: multiple independent "improve this same block of rendered text" ideas all want to touch the same already-escaped, already-highlighted pipeline, and each one adds its own risk of the two passes corrupting each other's output if not designed together.

6. Status and Open Questions

Nothing was decided and nothing was built. The brainstorming pass that led to this report was interrupted after its first clarifying question (field scope: status alone, status + incident_summary, or all narrative fields across all trackers) by the user's "just research" redirect, so that scope question is still open. If this is picked up again, the natural fork is Idea 2 (near-zero-cost, ships everywhere immediately, relies on an unverified convention) versus Idea 3 (thorough, hand-authored, real ongoing cost and staleness risk, same shape as the existing section_summaries feature) — they aren't mutually exclusive, and Idea 2 in particular could be evaluated cheaply since it needs no new data at all, only a render-time change and a check of how consistently the "Update:" convention actually holds across existing entries. Idea 1 looks like the weakest standalone candidate: it inherits the authoring/staleness cost of Idea 3 without matching Idea 3's thoroughness, and inherits the "what counts as key" judgment problem the original spec already flagged as unsolved for a related case.
