Gating Claude Code Cron Runs on Time, Tokens, and Budget — Discussion Report

The Accountability Project — Docs

Session Scope: A discussion, not an implementation — ideas for starting, stopping, and pausing Claude Code sessions launched from bash/cron based on conditions like time of day, tokens consumed, percentage of session/plan limits consumed, and estimated run time. No code has been written; this captures the idea space, the real mechanisms Claude Code exposes for each piece, and the open design choices.

1. Problem and Motivation

Claude Code on this machine runs on metered API credits with a documented $20/mo cap, not a flat subscription — project_claude_code_billing.md already flags this as an unresolved concern, specifically calling out that subagent dispatches are expensive and the root cause of unexpectedly high spend hasn't been pinned down. Any cron job that fires off a headless claude -p run unattended is exactly the scenario where that risk is sharpest: nobody is watching the terminal, so nothing stops a job from running long, dispatching subagents, or firing during a window it shouldn't, until the bill or the plan's rate limit is already blown. The idea explored here is a guard layer that sits between cron and claude -p, deciding whether a scheduled run is allowed to start at all, and a separate watchdog that can kill one that's already running if it exceeds a hard ceiling.

2. What "Start / Stop / Pause" Actually Map To

The three words in the prompt map to three genuinely different mechanisms, not three settings on the same dial:

  • Start is a pre-flight gate. Before cron's normal invocation of claude -p ..., a wrapper script checks conditions and either launches the real command or exits without launching it. This is the cheap, safe, and highest-leverage piece — most of the value in this whole idea comes from just not starting a run that shouldn't happen.
  • Stop is an external kill, not something the running process cooperates with. timeout <duration> claude -p ... gives a clean wall-clock cap for free. For a budget-based cutoff mid-run, nothing inside Claude Code's hook system currently offers a documented way for a hook to unilaterally terminate the whole agent loop from inside — hooks can deny an individual tool call (PreToolUse), but there's no "hook says stop the session now" primitive. The practical way to truly stop a run that's blowing through budget mid-flight is an external watchdog process tailing its usage and sending SIGTERM (then SIGKILL if it doesn't exit) once a ceiling is crossed.
  • Pause is better understood as defer, not freeze. Sending SIGSTOP to a claude -p subprocess mid-request would freeze the local process but not the in-flight HTTPS request/response sitting in the OS socket buffer — a long enough freeze risks the connection timing out on one end or the other, and there's no guarantee the API server tolerates an arbitrarily paused client gracefully. A cron-triggered job that shouldn't run right now is much more safely handled by not starting it and letting the next cron tick re-evaluate, than by trying to freeze and later resume an in-flight one.

3. Conditions and How to Measure Them

Time of day / day of week. The cheapest condition to check, and cron already half-solves it — a job's own crontab schedule can restrict which hours it fires at all. A guard script adds value on top of that mainly when the logic doesn't fit cron's field syntax cleanly (e.g., "also skip if a lid-closed or do-not-disturb flag file exists," combining a time window with an unrelated condition cron can't express).

Tokens consumed. Claude Code writes local session transcripts as JSONL under ~/.claude/projects/<project-path>/, and each message record carries its input/output token counts — this is the same data source the existing SessionEnd hook (already logging transcripts per feedback_session_save.md) has access to. A guard script can sum tokens over a lookback window (today, this rolling week) either by re-scanning those transcripts on each check (simple, more I/O, but no double-counting risk) or by having the SessionEnd hook append a one-line summary per run to a dedicated state log the guard script reads instead. ccusage — a known community CLI that parses these same local JSONL files into token/cost reports — is worth considering as an off-the-shelf accounting engine instead of writing a custom parser, if its output format is scriptable enough to feed a guard script's decision.

Percentage of session/plan limits consumed. This one depends heavily on the billing model, and Joe's setup is specifically metered-API rather than a Pro/Max plan — Pro/Max shows a rate-limit percentage in-session (/status), but that concept doesn't map cleanly onto API-key billing. For this account, the more relevant proxy is dollars of the known $20/mo credit cap consumed so far this billing period, computed from the same token counts times published per-token pricing (or from ccusage's cost output if it does this conversion already) rather than a "percent of limit" figure Claude Code itself exposes for this billing type.

Estimated run time. Nothing in Claude Code estimates this up front. The only grounded approach is empirical: log actual wall-clock duration per named job (not per run — per job definition, e.g., "nightly TAP recheck sweep" as a category) to the same state log, and before launching another instance of a known job, compare a rolling average or percentile of its own history against how much time/budget remains until the next blackout window or hard cap. A job with no history yet has no estimate, and the guard script should treat that as a reason to require an explicit conservative default rather than assume it's short.

4. Proposed Architecture

A small toolkit, sketched at the level of "what pieces would exist," not a spec:

  • usage_state.jsonl — one line appended per completed run: timestamp, job name, tokens in/out, estimated dollar cost, wall-clock duration, and exit reason (finished / timeout / killed / skipped). The skipped case matters as much as the completed ones — it's what lets you later ask "how often is the guard actually blocking something, and was it right to?"
  • guard.sh — what cron calls instead of claude -p directly. Runs pre-flight checks in cheap-to-expensive order (time window, then daily/weekly token or dollar budget from the state log, then estimated duration vs. remaining budget) and only then execs the real command, wrapped in timeout. A crontab entry becomes */15 * * * * guard.sh job_name with the actual command, default duration, and any per-job budget override defined in a small config the guard script reads by job name — mirroring the picker/config-driven pattern already used for TAP's proposed batch-picker tooling.
  • watchdog.sh — a separate, lightweight loop (its own cron tick, e.g. every minute, active only while a guarded job's PID file exists) tailing that job's live token usage and sending SIGTERM/SIGKILL if a hard ceiling is crossed mid-run — the safety net for when a job's own estimate turns out to be wrong, since guard.sh's pre-flight check can only ever be as good as the estimate it started with.
  • Hook integration — extending the existing SessionEnd hook (already writing transcript logs) to also append that run's totals to usage_state.jsonl, rather than introducing a second, separate logging mechanism alongside the one already in place.

5. Two Different Problems: Headless Cron Jobs vs. a Live Session

Everything above assumes the target is a headless, one-shot claude -p process launched fresh by cron — the natural case for "start/stop/pause from bash." A live interactive or long-running background session that cron wants to reach into and pause mid-conversation is a materially harder and different problem: it's a live network connection, not a process cron owns the full lifecycle of, and the SIGSTOP risk from Section 2 applies directly. The harness's own self-pacing mechanism (the dynamic-loop ScheduleWakeup pattern used by /loop) already solves the adjacent problem — a running session deciding for itself when to next wake up — but that's an in-session decision the session makes about itself, clamped to 60–3600 seconds per wakeup, not an external bash script reaching in from outside. It's not a substitute for cron-based gating of fresh headless runs, and cron trying to externally pause a live session is likely not worth pursuing versus just not starting one in the first place.

6. Open Questions and Next Steps

Nothing has been decided or built. Open questions worth resolving before this goes anywhere: whether to build custom token/cost accounting or lean on ccusage's existing parser; whether the dollar-budget check should read live from Anthropic's own billing/usage data if an API endpoint for that exists, versus reconstructing it locally from transcript token counts and published pricing; and whether this is worth building at all versus simply not scheduling unattended cron jobs that invoke Claude Code in the first place, given personal-scale usage may not justify the guard infrastructure's own complexity. If this moves forward, it should go through a proper brainstorming/scoping pass before any script gets written, the same way the TAP batch-picker idea did.
