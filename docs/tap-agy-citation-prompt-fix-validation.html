1. Summary

During live smoke-testing of agy_watch.py (2026-09-04, same session as its build — see docs/superpowers/specs/2026-09-03-agy-live-fabrication-detection-design.md), a real agy run against batch 12's records passed the log-check (real search activity detected) but failed the URL-check entirely: every finding in the brief cited "(Cannot find the specific article URL; sourced from Search Web summaries)" instead of a real link, despite agy having actually run searches. research_brief_prompt.md's citation instructions were strengthened the same day (commit 8e21be0) to make the "could not find" language a documented last resort rather than a default, and to require capturing a URL at the moment a search result is read rather than reconstructing one afterward. A second live run against the identical batch-12 input, through the same code path, went from 0 cited URLs (0 resolving) to 13 cited URLs (13 of 13 resolving, 100%), with the one remaining "could not find" case used correctly — for a claim the prompt's own rules say should stay unconfirmed rather than asserted. The fix is validated on this one controlled comparison; broader confidence would come from repeating it on a batch this exact prompt hasn't already been run against.

2. Background: The Citation Gap

While validating agy_watch.py's live fabrication-detection mechanism against a real agy run (not a fake test double), the tool correctly identified that agy had done genuine research — its CLI log showed real fetchFromTrawlerCache search-cache activity — but the resulting brief was still useless for triage: every one of its findings read as a variant of "(Cannot find the specific article URL; sourced from Search Web summaries, 2026)." Running verify_research_brief.py directly against that artifact confirmed it mechanically:

=== Checking agy tool-use in log ===
Tool-execution steps (CORTEX_STEP_TYPE_*): 0
Search-cache lookups (fetchFromTrawlerCache): 4
Pure text-generation calls (*GenerateContent): 23

=== Checking cited URLs in brief ===
URLs cited in brief: 0
  OK (resolved): 0
Explicit 'could not find a URL' admissions: 0 (phrasing varied slightly per finding, but every finding admitted no URL)

=== VERDICT ===
FAIL -- do not use this brief for triage.

This is a distinct failure mode from either of the original pilot's two batches (docs/reports/tech-reports/tap-agy-research-prepass-pilot-report.md): batch 12 had bare-domain citations (a homepage instead of an article), and batch 13 had zero tool use at all (pure fabrication). This run had real tool use and zero URLs of any kind — agy was searching, finding real information, and then declining to report where it came from, treating the prompt's own escape-hatch language ("if you cannot find the specific article URL for a claim, say so explicitly") as a default outcome rather than a last resort.

Re-reading research_brief_prompt.md's existing step 4, the phrasing gave agy an easy, always-available out with no requirement to have actually tried to recover a URL first — and step 2 never told it to capture a result's URL at the moment it read that result, leaving room to summarize findings from memory after the fact, by which point the URL was gone.

3. The Fix

Commit 8e21be0 (tap-data) changed two steps in tracker/research_brief_prompt.md, leaving the rest of the prompt (record fields, output format, confidence-rating rules) untouched:

Step 2 (search instructions) gained: "Your search results come with a real URL attached to each hit -- capture that URL at the same time you read the result, not after the fact from memory. If a result looks relevant but its URL isn't obviously the specific article ... fetch it to confirm and to recover the direct article link before citing it."

Step 4 (citation requirements) had its escape hatch tightened: the URL "must be one you actually captured from a search result or a fetch in this session -- never reconstructed from memory or guessed." "I could not find the specific article URL" becomes explicitly "a last resort, not a default: use it only after you already have a search result naming this specific finding and its URL genuinely was not exposed by the result or a follow-up fetch." A closing line addresses the exact failure pattern observed: "If every finding in a brief ends up with no specific article URL, that is a sign to redo the searches more carefully, not to conclude none exist."

No change was made to step 1 (source-URL verification), step 3 (the causal-link caution that drove the original pilot's batch-12 correction), step 5 (confidence rating), or the output format — the fix is scoped narrowly to the citation-capture behavior that broke.

4. Live Validation: Method

To isolate the prompt's effect from any other variable, the validation reused the exact same input as the failing run: output/research-briefs/batch12-input.json (records c0067 through c0072, unchanged) — a controlled before/after comparison against identical underlying facts, differing only in the prompt template.

The before run (pre-fix) was a bare agy invocation, run manually outside agy_watch.py, during that tool's own smoke-testing. The after run (post-fix, this validation) was run through agy_watch.py itself — the actual production entry point — rather than bare agy, so this also stands as a second live-fire validation of agy_watch.py's own kill/retry/log-check/URL-check pipeline, not just the prompt:

cd ~/gjoe/tap-data/tracker
python3 agy_watch.py \
  --input output/research-briefs/batch12-input.json \
  --output /tmp/citation-fix-test-brief.md \
  --log /tmp/citation-fix-test-agy.log \
  --grace-period 120 --poll-interval 5

Total wall-clock time: ~268 seconds (4m28s), comparable to the earlier successful agy_watch.py validation run (216s / 3m36s) on a different, non-citation-focused test. agy_watch.py exited 0 (full PASS) without needing its retry path — real signal appeared well within the grace period, same as every other healthy run observed so far.

The one remaining "could not find" case in the after-run brief (cluster c0068, the DRC illness/Ebola-conflation cluster the original pilot's own batch-12 correction is about) reads: "Possible link, unconfirmed: In May 2026, a separate and confirmed Ebola outbreak ... was declared ... which appears to be a distinct event from the early 2025 illness. (I could not find the specific article URL, but the events are treated as distinct)." That is exactly the prompt's step 3 behavior working as intended — a claim without a source explicitly asserting the link stays hedged rather than settled fact — not a citation failure. Every other finding across all six clusters carries a specific, dated, outlet-attributed, resolving URL, matching the prompt's required format (e.g. https://friendsofcancerresearch.org/blog/stakeholder-connect-from-guidance-to-action-what-operation-trialblazer-means-for-the-future-of-oncology-drug-development/ — Friends of Cancer Research, June 2026).

6. Verdict

The fix resolved the observed failure mode on this one controlled comparison: same input, same underlying facts, only the prompt changed, and citation quality went from 0-of-0 to 13-of-13 resolving URLs. This is one data point, not a statistical sample — agy's behavior has shown batch-to-batch variance before (the original pilot's two batches each failed differently), so the appropriate next step is watching citation quality on the next real, previously-unseen batch this exact prompt runs against, not treating this single rerun as proof the citation-omission failure mode can never recur. No regression was introduced: step-1 through step-5 behavior otherwise unrelated to citations (confidence ratings, the causal-link caution, non-representative-record handling) all still produced output matching the established format.

This validation run also incidentally re-confirms agy_watch.py's own live mechanism (log-check, no false kill on a healthy ~4.5-minute run, exit code 0 on full pass) on a second, independent real invocation beyond the one covered in its own build session.
