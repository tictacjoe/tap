TAP Recheck Automation — Batch-Picker Design Report

The Accountability Project — Docs

Session Scope: A brainstorming session exploring programmatic control over Claude Code operations via bash/Python, narrowed through clarifying questions to a concrete pilot: mechanizing the CLA/GSR recheck sweeps' batch-picking method into a script, with a feedback loop that revises the script itself (rather than accumulating prose lessons in memory) when sessions surface bugs. The session produced a proposed design, presented in chat and captured here; no code has been written and no formal spec has been committed yet.

1. Session Overview

The session opened with an open-ended idea: exploring programmatic control through bash and Python over Claude Code operations, with a dev feedback loop in which Claude modifies its own controlling scripts based on functional experience and user feedback. Following the brainstorming process for architectural work, the idea was classified as architectural (a new subsystem, not a change to an existing flow) and narrowed through a sequence of clarifying questions before any design was proposed. The narrowing converged on a specific, already-recurring task to pilot the idea against: the CLA (Cabinet-Level Accountability) recheck-sweep batch-picking method documented in the reference_tap_cla_recheck memory, which is currently prose Claude re-reads and manually re-executes every session rather than code.

2. Problem and Motivation

The reference_tap_cla_recheck memory file's "Standing research lessons" section has accumulated several lessons that are not judgment calls but mechanical bugs: a recurring batch-number off-by-one drift ("something outside this memory keeps advancing the count independently"), an exclusion window that was sized in batch-count rather than calendar time (missed CLA batches 44–46 because 44–49 ran in one marathon session), and a bulk field-rename commit producing a false "recently touched" signal in the stale-entry finder's age score. Each of these was discovered once, written up as a paragraph, and then had to be manually re-applied by a human or Claude re-reading that paragraph in every subsequent session — the lesson persisted, but the fix did not.

This gap is exactly what the session's original framing was probing for: a feedback loop where functional experience (a batch session hitting a bug) and user feedback lead to the controlling script being revised, so the fix is enforced by code the next time rather than depending on someone re-reading and re-applying prose.

3. Scoping Decisions

Three clarifying questions shaped the pilot before any design was proposed:

  1. Primary use case. Of three framings offered — recurring personal automation, a general orchestration harness, or an experiment in self-modifying automation where the task domain is secondary — the third was chosen, with an explicit interest in applying it to TAP specifically.
  2. Autonomy model. Of three levels — Joe-in-the-loop, autonomous within guardrails, or a fully autonomous unattended loop — Joe-in-the-loop was chosen, on the same trust model as normal Claude Code editing (Claude proposes a diff, Joe reviews/approves). This was chosen with the observation that in-session self-correction already happens routinely; the novel part is persisting that correction into a script rather than just recovering from it live.
  3. Invocation mechanism. Offered a choice between headless CLI calls (claude -p), the Claude Agent SDK, or a recommendation — the recommendation was deferred to this session's judgment.

A fourth decision followed from evaluating three concrete approaches (Section 4): the pilot is scoped to the CLA tracker only, not all three trackers (CLA, GSR, Corporate Deregulation) at once, since CLA is the most actively exercised tracker (batch 54 as of this session) and the goal is to prove the pattern on one concrete case before generalizing.

4. Approaches Considered

Three approaches were presented, with a recommendation:

Approach A — Deterministic batch-picker plus run-log, refined in place (recommended and selected). Port the batch-picking method into a standalone Python script Claude invokes via Bash during normal interactive TAP sessions, logging each run's picks and outcomes to a structured file. When a session hits a bug or a mechanical lesson, the fix lands in the script as a normal reviewed code change rather than as a new memory paragraph.

Approach B — Headless orchestration layer. A wrapper script shelling out to claude -p to run whole batches non-interactively, applying the same self-editing loop to prompt templates and flags instead of picker logic. This is closer to the literal framing of "programmatic control over Claude Code operations," but TAP recheck work is deliberately judgment-heavy — advisor() calls, primary-source verification, an explicit "correctness over deadline" standard already in memory — and running it headless works against a workflow that has already been deliberately tuned to be interactive. It also carries real cost exposure given the unresolved metered-billing concern already tracked in memory.

Approach C — General harness first, TAP as the first registered task. Build reusable orchestration infrastructure before picking a concrete pilot task. Rejected as front-loading design cost on speculative generality before the core hypothesis — that persisting lessons into code beats persisting them into prose — has been tested on even one concrete case.

Approach A was selected as the smallest test of the core hypothesis, fully within the Joe-in-the-loop trust model already agreed on, with Approach B available as a natural follow-on if A proves useful and less-interactive runs become desirable later.

5. Proposed Design

New file: tap-data/tools/batch_picker.py (new tools/ directory), a standalone, read-only script — no LLM calls, no commits, no edits to tracker data. It sits alongside the existing prosecution/find_stale_prosecution_entries.py, which it calls rather than replaces: the finder still does schema-level flagging (contested entries, stale last_verified, low/moderate confidence tiers); the new script does the pick.

Invoked as python3 tools/batch_picker.py cabinet-level, it performs, in order:

  1. Runs the existing finder to get the flagged-entry pool.
  2. Computes the next batch number from git log --oneline --grep=batch -- prosecution/cabinet-level alone, with no dependency on the memory file's "current state" section. If a second signal (e.g. batch-notes filenames) disagrees, both are printed and the script stops rather than guessing — the fix for the recurring off-by-one drift.
  3. Builds the exclusion set from commits in the last N days (default 14, configurable), using git show --name-only per commit rather than a last_verified-age proxy — this is also what already sidesteps the bulk-rename false-positive bug without any new logic, since that bug is specific to the age-proxy approach the finder script uses, not to a commit-based exclusion set.
  4. Ranks the remaining candidates by the existing dated-hook keyword list (hearing, oral argument, scheduled, deadline, sentencing, circuit, markup, cloture, briefing, etc.).
  5. Picks roughly six entries for topical diversity, filling from the zero-score pool when fewer than six qualify.
  6. Prints the picks with their evidence (matched keywords, excluded commit SHAs) and appends one JSON line to tools/batch_picker_log.jsonl — batch number, exclusion window used, candidates considered, the picks, and an outcome field left null for Claude to fill in by editing that line once the recheck session has determined each pick's tier (real-correction, moderate, or light-touch).

6. The Feedback-Loop Mechanism

This is the part of the design that directly answers the session's original framing. When a recheck session hits a bug or a mechanical lesson — the kind already cluttering the memory file today — the fix is made to batch_picker.py or its tests as a normal, Joe-reviewed commit in tap-data, not as another memory paragraph. Once this ships, reference_tap_cla_recheck gains a one-line note that mechanical batch-picking bugs now belong in the script and its tests, not in memory; the memory file keeps only lessons that remain genuine judgment calls, such as the literal-text test distinguishing a moderate update from a real correction.

The run-log also converts what are currently one-off anecdotes into checkable data. The memory file's claim that an all-zero-score diversity pick still produced six real corrections at batch 40 is presently a single remembered data point; once several batches have run through batch_picker.py, the same question — do zero-score diversity picks find real corrections as often as that anecdote suggests — becomes a jq query against batch_picker_log.jsonl instead.

7. Testing and Error Handling

A companion tools/test_batch_picker.py was proposed, matching the repository's existing test convention (prosecution/test_build_prosecution_index.py, government-services/test_validate_section_summaries.py, etc.), covering the exclusion-window date math, keyword ranking, diversity-pick logic, and batch-number parsing against fixture data rather than the live repository's git history. Before the script is trusted for a real batch, the plan calls for running it once against the actual repository and comparing its picks to what a manual session would choose.

Error handling follows a fail-loudly, no-silent-fallback rule: no flagged entries, no batch commits found for the tracker, or two disagreeing batch-number signals all stop the script with an explicit message rather than guessing — mirroring the existing standing instruction (already in the CLA recheck memory) to confirm a mismatched batch number with Joe rather than silently resolving it.

8. Status and Next Steps

Nothing has been built yet. This report documents a design presented and discussed in chat during this session; the design has not yet been given an explicit go-ahead to proceed to implementation, and no spec file has been written to docs/superpowers/specs/ under the normal brainstorming-to-writing-plans flow. The pilot as designed is intentionally small — one new script plus one test file, touching no existing tracker data or tooling — so the remaining decision is whether to proceed straight to implementation given that scope, or to first write and commit a formal spec document before an implementation plan is drafted.
